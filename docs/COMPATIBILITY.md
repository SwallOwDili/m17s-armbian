# 兼容性与验证边界

目标硬件是天猫魔盒 M17S：Amlogic S905X、P212 兼容板、2 GiB RAM、Samsung
8GME4R eMMC（7818182656 bytes）。配置文件见 `profiles/m17s.json`；它约束了
P212 设备树及 eMMC 分区范围；安装器运行时探测设备，不能仅凭 `mmcblk2` 名称判断目标。

当前锁定 Linux 内核为 **6.12.109**，基础镜像为 Armbian Bookworm arm64 server。下文硬件矩阵覆盖 rc2 镜像；rc3 安装器源码目前只有单元测试结果。
0.1 版本禁止更换内核字节或升级内核；维护流程只允许在内核和根 UUID 保持不变时刷新
受支持的 initrd/DTB，同版本号的另一份内核也不视为兼容。用户空间软件更新不等于内核升级。
首次 USB 引导以原厂 U-Boot 已完成并验证 vendor multiboot 激活为前提。原厂 Android
侧的 multiboot 激活必须先完成并验证；它与 installer 写入引导分区是两个不同步骤，
本项目不在此处提供未经验证的新激活命令。

RAM handoff 的必要性在于：vendor U-Boot 负责从 eMMC 预加载内核、initrd、设备树和
第二阶段脚本，然后跳转到受控的主线 U-Boot/引导流程。各载荷使用互不重叠的固定内存
区域，避免加载时覆盖彼此或跳转代码：U-Boot 从 `0x01000000`，DTB 从 `0x08008000`，
内核从 `0x08080000`，initrd 从 `0x13000000`，脚本槽位到 `0x22000000`。`boot.py`
会在生成前检查这些边界；这也是该 handoff 方案的保护条件。

ARM64 Image 头的 `image_size` 表示有效内存占用，可能大于文件长度；校验器按该值检查
内核与 initrd 是否重叠，不能要求它恰好等于文件字节数。依据见
[Linux ARM64 启动协议](https://docs.kernel.org/arch/arm64/booting.html)。

rc2 已在这一台符合上述配置的样机上完成以下验收，不能据此推断其他板型或所有外设兼容：

| 项目 | 结果 |
| --- | --- |
| eMMC 安装与启动 | 真实安装通过，前 700 MiB、boot0/boot1 与分区间隙保持不变；最终拔除 USB 后的物理断电启动通过 |
| 最终 rc2 USB | 镜像覆盖范围完整读回通过；原版参数两次连续冷启动复测通过，但此前一次内核早期卡住尚未定位 |
| HDMI、有线网络 | 两次 USB 复测和最终 eMMC 启动均确认 HDMI 登录提示，公钥 SSH、sudo 和服务检查通过 |
| 控制台服务 | rc1 首启竞态已修复；上述成功启动的服务顺序正确，失败服务为 0 |
| Bluetooth | 初始化出现 BCM baudrate/reset 超时 -110，未通过 |
| rc2 原版镜像的 Wi-Fi、音频、本地键盘交互 | 未验证；下述音频结果来自安装额外软件和配置后的实验系统 |

## 后续多媒体实验

补充安装 Mesa、GStreamer、Weston 并采用 CMA 768 MiB 实验 DTB 后，基础 GPU/EGL 渲染可运行；
真实 HEVC Main10 4K 电影片段经 V4L2 硬解、Weston 合成后输出 1080p，用户确认画面流畅。
随后启用主板模拟音频口，预先下混的立体声 PCM 有声且用户确认音画基本同步；盒子原生 TrueHD、DTS-HD MA、AC-3 固定音轨解码也完成。原音轨复播有声，但用户报告启停异响；实验性多音轨切换测试未通过，播放器级切轨尚未完成，HDMI 听感未验收。
爆音定位显示模拟链路首次进入工作状态仍有一次瞬态；可选常驻服务配合 0.75 秒淡入淡出后，独立测试音和实际电影的开始、结束均确认无爆音，但首次上电爆音仍存在。HDR→SDR 的 GL 试验在尚未加入色调映射时已低于实时速度，不能作为当前解决方案。
直接使用 KMS 视频图层仍曾黑屏；HDR 色彩适配尚未完成，长期稳定性尚未验收。完整结果见[多媒体实测](MULTIMEDIA.md)。
此实验没有重建 rc2 镜像，不改变上表所述原版发行物的验收边界。

HDMI 登录提示不等同于本地键盘登录测试。完整备份已核对 CRC、长度与 SHA-256，
但实际还原、安装中断恢复和长期稳定性未验收。旧系统的启动记录不计入 rc2 验收。
此前误称“第二次拔 USB 冷启动”的观测已撤回该分类：它只证明系统从 eMMC 运行、采集时未枚举 USB，不能证明物理拔盘或断电操作。
